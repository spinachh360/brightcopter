# Firebase Hosting — Bright Copter

Project: `brightcopter-337b5`. Default Hosting site: `brightcopter-337b5`.
Expected production address: `https://brightcopter-337b5.web.app`.

This is **Firebase Hosting**, serving static files. The website does not need
App Hosting, Cloud Functions, Firestore, a Firebase web SDK or client API keys.
The existing WhatsApp order flow runs in the browser. The project's current
Firebase plan and Hosting quotas still apply; these scripts do not change billing.

## Prepare and check

Use Node 24 (`.nvmrc`) and the `firebase-hosting` GitHub branch:

```bash
git clone --branch firebase-hosting https://github.com/spinachh360/brightcopter.git
cd brightcopter
npm ci
npm run firebase:build
npm run firebase:check
```

The build takes the project from `.firebaserc`, rebuilds all canonical/social
URLs, sitemap and schema for the Firebase address, and generates native
`firebase.json` headers with current CSP hashes. An ignored build receipt ensures
that the files, headers and target project still match at deployment time.

For a fast editing preview use `npm run dev`. For Firebase's actual local routing:

```bash
npm run firebase:serve
```

Open `http://127.0.0.1:5000`. This starts only the local Hosting emulator with a
demo project; it does not publish files. For automated Hosting/browser checks:

```bash
npx playwright install chromium
npm run firebase:test
```

The checks cover clean route URLs, direct/reloaded product pages, real 404s,
legacy policy redirects, headers/CSP, asset caching and the sitemap. The Hosting
emulator does not need Java. `firebase:check` also needs the Playwright browser.

## Sign in and publish

In Firebase Console, select `brightcopter-337b5` and open **Build → Hosting**. If
Hosting has not been enabled yet, complete its Get started step for the default
site. This repository already contains the Hosting configuration.

Run in your own terminal, completing Google's sign-in prompts there:

```bash
npm run firebase:login
npm run firebase:deploy
```

`firebase:deploy` rebuilds and verifies the site, then deploys **Hosting only** to
the selected project. A successful CLI response supplies the actual Hosting URL.
Opening the URL must be verified after publishing; having these files does not
mean the site has already been deployed.

If you only have a browser, use [Google Cloud Shell](https://shell.cloud.google.com/?project=brightcopter-337b5)
with the Google account that owns this Firebase project. Its terminal can run
the same commands without downloading the project to your phone or computer:

```bash
git clone --branch firebase-hosting https://github.com/spinachh360/brightcopter.git
cd brightcopter
nvm install
npm ci
npm run firebase:login
npm run firebase:deploy
```

`nvm install` uses the checked-in `.nvmrc` to select Node 24. Complete the Google
sign-in prompts in your own terminal/browser; no sign-in code needs to be sent here.

To publish an expiring, non-indexed review link instead of production:

```bash
npm run firebase:preview -- --channel review
```

Preview builds have `noindex,nofollow`, an empty sitemap and an `X-Robots-Tag`
header. To prepare this mode locally without publishing, use
`npm run firebase:build:preview` followed by `npm run firebase:test` or
`npm run firebase:serve`. A production predeploy rejects preview output.
Production deploys always rebuild production metadata. Use local previews
while editing and publish completed batches. GitHub pushes alone do not publish
to Firebase; no automatic deployment workflow or billing changes are installed.

## Other site IDs and custom domains

If Firebase Console shows a different Hosting site ID, supply it explicitly:

```bash
npm run firebase:deploy -- --site YOUR_HOSTING_SITE_ID
```

After verifying a custom domain in Firebase Console, select its canonical URL:

```bash
npm run firebase:deploy -- --url https://your-domain.example
```

`--project` can explicitly select another project. The wrapper deliberately
overrides an obsolete `SITE_URL` in local environment files; the default is the
selected site's `web.app` origin. A custom origin is selected using `--url`.
The old `brightcopter.netlify.app` hostname belongs to Netlify and cannot be
transferred to Firebase. The old site is not removed by these commands.

Saved bags and prepared requests are browser storage tied to each website
origin. The Firebase address starts with separate storage; it does not import
the old Netlify browser data. Messages already sent in WhatsApp remain there.

## Files and credentials

- `config/firebase.mjs`: Hosting routing, cache and emulator configuration.
- `firebase.json`: generated by each build; includes native Firebase headers.
- `scripts/firebase.mjs`: pinned Firebase CLI 15.34.2, build/verification/deploy commands.
- `.firebaserc`: public project alias, not a credential.
- `.firebase/cli-config`: local OAuth/CLI state, ignored and excluded from ZIPs.
- `.firebase-build.json`: ignored build receipt; never part of the uploaded site.

The wrapper defaults to the explicit Firebase login rather than unrelated ambient
Google application credentials. CI can deliberately set `FIREBASE_USE_ADC=true`
with an authorised Google workload identity; never commit credentials or expose
them through `VITE_*`. No passwords, OAuth codes or service-account keys need to
be shared in chat. The generated upload ignores hidden files, build manifests,
Netlify configuration files and local authentication state.

`netlify.toml` and Netlify output are retained for rollback. Firebase applies the
headers/redirects in `firebase.json` instead. There is no SPA wildcard rewrite:
prerendered route directories serve the pages and `404.html` serves missing URLs.
